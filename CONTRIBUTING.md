# Contributing to cepheus-emulator

Thank you for your interest in contributing to **cepheus-emulator**!

This project adheres to a strict engineering standard: **clean-room native emulation without synthetic mocks or fake progress markers**. Before contributing, please take a moment to review this document to understand our workflow, coding standards, and verification requirements.

---

## 1. Core Principles

1. **Native over Mocked**: All device models (CPU, GICv3, GENI UART, Clocks, TLMM, PMIC, UFS, SMMU) must interact natively with unmodified guest drivers via realistic MMIO, IRQ, or DMA contracts.
2. **Strict Stub Allowlist**: Only components officially listed in the stub allowlist (see [Section 4](#4-stubbing-policy)) may return stubbed responses. DTB modifications are permitted only to disable allowlisted subsystems.
3. **Empirical Evidence**: Every milestone claim requires raw, reproducible evidence captured via `tools/capture.py`. Hand-written logs or assertions on synthetic strings are considered fraudulent and rejected by CI.

---

## 2. Milestone-Driven Workflow

All work in `cepheus-emulator` is structured around sequential milestones defined in [`milestones.json`](milestones.json).

### Branching Model

* `main` is our production trunk and must remain green (`make ci` passes at all times).
* Work for a specific milestone must take place on a dedicated branch named:
  ```
  m/<MILESTONE_ID>-<slug>
  ```
  *Example*: `m/R0-host-doctor`, `m/R4-geni-uart`

### Working on a Milestone

1. **Verify dependencies**: Ensure all preceding milestones (`depends`) are `VERIFIED`:
   ```bash
   python3 tools/milestone.py list
   ```
2. **Transition state**:
   ```bash
   python3 tools/milestone.py set <ID> IN-PROGRESS --note "Implementing native model"
   ```
3. **Capture evidence**:
   Produce both a **positive** test log and a **negative** test log (where the feature is deliberately disabled to prove cause-and-effect):
   ```bash
   # Positive test
   python3 tools/capture.py --out evidence/<ID> --name positive -- <command...>

   # Negative test (feature disabled/broken)
   python3 tools/capture.py --out evidence/<ID> --name negative -- <command_with_breakage...>
   ```
4. **Verify against spec**:
   ```bash
   python3 tools/milestone.py verify <ID>
   ```
5. **Run the local CI suite**:
   ```bash
   make ci
   ```

---

## 3. Forbidden Practices (Anti-Mock Policy)

Automated scanners ([`tools/mockscan.py`](tools/mockscan.py)) enforce strict static checks across every commit. The following patterns will fail CI:

* Scripts echoing fake success strings (e.g. `echo "..._VERIFIED"`, `echo "..._PASSED"`).
* Test suites asserting against output generated by their own harness rather than real guest state.
* Hardcoding command output (e.g. `pm list`, `uname`, `getprop`, service lists).
* Defining `Mock`, `Fake`, `Simulator`, or `Simulated` classes in Python/C.
* Manually setting properties (e.g. `setprop sys.boot_completed 1`).
* Using `-machine virt` or generic kernels instead of `-machine cepheus` with the stock kernel.

---

## 4. Stubbing Policy

Only the following categories may be stubbed:

| Category | Permitted Scope |
|---|---|
| `boot_rom_chain` | PBL/XBL/ABL secure boot handoff state reproduction |
| `trustzone_qsee` | Secure world SCM/SMC error or test-only return codes |
| `modem_dsp` | Modem, Hexagon ADSP/CDSP/SLPI remoteprocs |
| `gpu_adreno` | Adreno 640 software rendering fallback |
| `camera_isp` | Camera ISP and imaging sensors |
| `sensors_biometrics_nfc_gnss` | Sensor hub, fingerprint, NFC, GNSS |

If a stub is required:
1. Register it in [`stubs/REGISTRY.json`](stubs/REGISTRY.json) with path, category, and a detailed explanation.
2. Annotate the stub implementation file with a comment containing `STUB(<category>)`.

---

## 5. Security & Sensitive Data

* **Never commit firmware**: Stock partitions, raw archives, or extracted images under `firmware/` must never be added to git.
* **Never commit secrets**: Environment files (`.env`, `.env.*`) must never be tracked or printed.
* **Host safety**: Never execute commands that touch raw host block devices (`/dev/sd*`, `/dev/nvme*`, `/dev/mmcblk*`) or connected physical devices.

---

## 6. Pull Request Process

1. Ensure your branch is rebased on latest `main`.
2. Verify all checks pass locally:
   ```bash
   make ci
   ```
3. Push your branch and open a Pull Request against `main`.
4. Include a concise summary in the PR description following this format:
   ```markdown
   ### Milestone: <ID> (<TITLE>)
   - **Status**: VERIFIED
   - **Positive Evidence**: `evidence/<ID>/positive.log`
   - **Negative Test**: `evidence/<ID>/negative.log` (<description of intentional breakage>)
   - **Stubs Added**: <none or list from stubs/REGISTRY.json>
   ```
5. CI will run automated mock scanning and milestone verification on GitHub Actions.
